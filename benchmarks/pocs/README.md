# WASM GC & Componentize Proof-of-Concepts

Evaluated against the Ephemora Cell sandbox
(wasmtime-py 47.0.1, wasmtime CLI 34.0.0, wasm-tools 1.255.0, Python 3.14.3,
Rust 1.92.0 with `wasm32-wasip1`/`wasm32-wasip2` targets).

Two PoCs:

| PoC | Directory | What it proves |
|-----|-----------|----------------|
| WASM GC | `gc_poc/` | GC types (struct/array/ref) run under both sandbox ABIs; fuel/epoch/memory limits apply; compile+runtime cost vs an arithmetic twin |
| Componentize | `componentize_poc/` | Lifting preview1 core modules into WASI-0.2 components with `wasm-tools component new` + the preview1→0.2 command adapter, then running them through `ComponentSandbox` |

Both are **standalone scripts + docs, NOT part of the pytest suite**.

---

## 1. GC PoC — `gc_poc/`

### What was built

All modules are generated by `build_modules.py` (`.venv/bin/python benchmarks/pocs/gc_poc/build_modules.py`):

| Artifact | Kind | Purpose |
|----------|------|---------|
| `gc_workload.wat/.wasm` | preview1 core, `_start` | 100k iterations of `struct.new $pt` + `array.new $at` + `struct.get`/`array.set` churn with a folded checksum; prints via `fd_write`, exits 0 |
| `arith_workload.wat/.wasm` | preview1 core, `_start` | non-GC arithmetic twin — identical trip count, pure `i32` ops |
| `gc_infinite.wat/.wasm` | preview1 core | unbounded GC churn (fuel / epoch tests) |
| `gc_grow.wat/.wasm` | preview1 core | GC alloc + linear `memory.grow`; traps (`unreachable`) when growth fails |
| `gc_core.wat/.wasm` | self-contained GC core | no WASI imports, direct `run` export, 100k GC iterations |
| `gc_wrapper.wat/.wasm` | **hand-written component** | wraps `gc_core` via `canon lift`, direct `run` export (no adapter involved) |
| `gc_wrapper_inf.wat/.wasm` | hand-written component | infinite-GC twin of the wrapper (fuel/epoch in component ABI) |
| `lifted.wasm` | lifted component | `gc_workload` lifted with `wasm-tools component new` + command adapter |

GC types used: `(type (sub (struct (field i32) (field i32))))`, `(type (sub
(array (mut i32))))`, `struct.new` / `struct.get` / `array.new` / `array.set`,
`(ref null $t)` locals.

### GC status in the sandbox engine config — VERIFIED ENABLED

The sandbox never touches `Config.wasm_gc` — neither `WASISandbox.run()`
(`wasi_runtime.py:294-304`), nor `ComponentSandbox.run()` (`wasi_02.py:147-154`),
nor the `EnginePool` (`engine_pool.py:100-107`). wasmtime 47 enables the GC
proposal in the default `Config()`.

Reproduce:
```
.venv/bin/python - <<'EOF'
import wasmtime, tempfile, os
wat = b'''(module
  (type $pt (sub (struct (field i32) (field i32))))
  (func (export "run") (result i32)
    (struct.new $pt (i32.const 7) (i32.const 8)) drop i32.const 0))'''
p = os.path.join(tempfile.gettempdir(), "gc_probe.wasm")
open(p, "wb").write(wasmtime.wat2wasm(wat))
m = wasmtime.Module(wasmtime.Engine(), open(p, "rb").read())   # OK: GC on
c = wasmtime.Config(); c.wasm_gc = False
wasmtime.Module(wasmtime.Engine(c), open(p, "rb").read())      # WasmtimeError
EOF
```

| Scenario | ABI | max_fuel | timeout | mem | Result |
|---|---|---|---|---|---|
| `gc_workload` success | preview1 | 100M | 30s | 128MB | **SUCCESS**, stdout `gc-workload done (100000 iterations)` |
| `arith_workload` success | preview1 | 100M | 30s | 128MB | **SUCCESS** |
| `gc_infinite` fuel exhaustion | preview1 | 50k | 30s | 128MB | **FUEL_EXHAUSTED** (`all fuel consumed` in `gc_loop`) |

| `gc_workload` GC-heap-only churn | preview1 | 100M | 30s | **1 MB** | **SUCCESS** — GC heap is NOT bounded by `Store.set_limits` (see Findings) |
| `gc_wrapper` (hand-written component) | component | 100M | 30s | 128MB | **SUCCESS**, exit 0 |
| `gc_wrapper_inf` fuel exhaustion | component | 10k | 30s | 128MB | **FUEL_EXHAUSTED** |
| `gc_wrapper_inf` epoch timeout | component | none | 1s | 128MB | **TIMEOUT** after ~1006 ms |
| `gc_workload` lifted (`lifted.wasm`) | component | 100M | 30s | 128MB | **SUCCESS**, stdout captured through the adapter |

### GC vs non-GC numbers (same loop count = 100 000)

| Metric | GC workload | Arith twin | Ratio |
|---|---|---|---|
| `wat2wasm` compile (best of 20) | 0.032 ms | 0.028 ms | 1.14x |
| wasmtime `Module.from_file` (best of 10) | 0.285 ms | 0.233 ms | 1.22x |
| sandbox run, median of 5 (incl. sandbox setup) | 3.93 ms | 0.37 ms | **10.6x** |
| fuel consumed (median, deterministic) | 3 416 396 | 1 516 396 | **2.25x** |

Fuel is **deterministic** and **enforced on GC-heavy loops** in both ABIs —
`struct.new`/`array.new` are ordinary instructions and metered like everything
else. GC allocation is ~4.7x more expensive *per unit of fuel* than the
arithmetic twin (10.6x wall-clock / 2.25x fuel), which is the price of the
collector and the larger per-instruction cost of typed GC ops.

## 2. Componentize PoC — `componentize_poc/`

### Pipeline

```
wasm-tools component new <preview1.wasm> \
    --adapt adapters/wasi_snapshot_preview1.command.wasm -o <lifted>.wasm
```

> **Note on "automatic" adapters:** `wasm-tools 1.255.0 component new` does
> **not** embed the preview1→WASI-0.2 adapter automatically. Without
> `--adapt` it fails:
> `failed to resolve import wasi_snapshot_preview1::fd_write` / `module
> requires an import interface named wasi_snapshot_preview1`.
> The adapter file (`wasi_snapshot_preview1.command.wasm`, 53 KB) is not
> bundled with wasm-tools or wasmtime-py; it was taken from the wasmtime
> v34.0.0 GitHub release and is vendored at
> `componentize_poc/adapters/wasi_snapshot_preview1.command.wasm` (adapter
> not retained in the repo — regenerate via the wasmtime v34.0.0 release).

Modules (built by `build_modules.py`):

| Preview1 core module | Description | Lifted output |
|---|---|---|
| `p1_print.wat` | hand-written wat, `fd_write` + `proc_exit(0)` | `p1_print_lifted.wasm` |
| `p1_loop.wat` | infinite `_start` loop (fuel/epoch) | `p1_loop_lifted.wasm` |
| `p1_grow.wat` | `memory.grow` until limit → `unreachable` | `p1_grow_lifted.wasm` |
| `rust_fs.wasm` | Rust `wasm32-wasip1` (sources in `rust_fs/src`, `cargo build --target wasm32-wasip1 --release`): prints args + `EPHEMORA_*` env, writes `<argv[1]>/out.txt` | `rust_fs_lifted.wasm` |

All lifted components export the command world `wasi:cli/run@0.2.3` (the
native fixture `tests/fixtures/hello02.wasm` exports `wasi:cli/run@0.2.6`).
`ComponentSandbox._find_run_func` matches the `wasi:cli/run@` prefix so both
versions are found; hand-written `run`-export components keep working via the
direct-`run` fallback. **No entry-point lookup breakage.**

### Scenario results (`run_componentize_poc.py` → `results.json`)

| Scenario | Result |
|---|---|
| Output capture (`p1_print_lifted`, `proc_exit(0)` path) | **SUCCESS**, `stdout='lifted-preview1: hello'` via custom sink |
| Output capture (`rust_fs_lifted`, normal `_start` return) | **SUCCESS** |
| `run_wasm(abi="auto")` on a lifted component | **SUCCESS** (magic-byte dispatch works) |
| Args + env + filesystem preopen (`rust_fs_lifted`, `args=[dir]`, `allow_env`, `allow_dirs`) | **SUCCESS**: `arg0=wasm-module`, `arg1=<dir>`, `env_ephemora_test=42`, `out.txt` written with `pwned-by-lifted-rust` |
| Fuel exhaustion (`p1_loop_lifted`, max_fuel=50k) | **FUEL_EXHAUSTED** |
| Epoch timeout (`p1_loop_lifted`, fuel=None, 1s) | **TIMEOUT** after ~1006 ms |
| Memory limit (`p1_grow_lifted`, max_memory_mb=2) | **ERROR** (`unreachable` after grow fails at 2 MB) |
| Memory limit control (max_memory_mb=128, 1400 pages ≈ 87.5 MiB) | **SUCCESS** |
| Preopen allowlist deny-by-default (`rust_fs_lifted`, no `allow_dirs`) | file **NOT** written (guest silently swallowed EACCES; status SUCCESS) |
| Preopen allowlist allow (`allow_dirs=(target,)`) | file written |

### Startup overhead (median of 7 sandbox runs, sandbox-setup inclusive)

| Component | median | vs native fixture |
|---|---|---|
| `hello02.wasm` (native Rust wasm32-wasip2 fixture) | 11.17 ms | 1.00x |
| `p1_print_lifted.wasm` (hand-written wat + adapter) | 2.41 ms | **0.22x** |
| `rust_fs_lifted.wasm` (Rust wasip1 + adapter) | 15.6 ms | **1.40x** |

Lifting adds the adapter (~19 KB into the component) but no measurable
startup penalty: the lifted hand-written wat component is 5x *faster* than
the native fixture (no Rust std runtime). The lifted Rust module costs ~30%
more than the native wasip2 fixture (preview1 adapter indirection + the
module's own startup), but everything stays in the same order of magnitude.

### What broke (all resolved for this PoC)

1. **Clean `proc_exit(0)` reported as ERROR** (pre-fix): the adapter
   forwards `proc_exit` to `wasi:cli/exit`, and wasmtime raises
   `Exited with i32 exit status 0` — `ComponentSandbox` classified it as a
   generic ERROR. **Fixed in runtime — see Finding 1.** After the fix
   `p1_print_lifted` reports SUCCESS.
2. **Lifting a module without an exported memory fails**: the command
   adapter imports `env::memory`, so a `_start`-only module (no `memory`)
   cannot be lifted (`main module cannot import memory`). `p1_loop` needed
   `(memory (export "memory") 1)` — every real command module exports one.
3. **`memory.grow` failure is silent**: `memory.grow` returns -1 rather than
   trapping, so limit tests must check the result (`i32.eq -1 → unreachable`).

## 3. Findings — sandbox gaps

### Finding 1 (FIXED, flagged loudly) — clean exit code 0 from a lifted component reported as ERROR

`ephemora_cell/wasi_02.py` — `ComponentSandbox.run()`'s trap handler.

* **Symptom:** any preview1 module whose `_start` calls `proc_exit(0)` (or
  any future component that calls `wasi:cli/exit#exit` with `ok`) exits
  through the host's `exit` implementation, which raises
  `Exited with i32 exit status 0`. The handler classified it as
  `ERROR` with `exit_code=1`, despite a clean exit and captured stdout.
* **Reproduce (pre-fix):**
  ```
  .venv/bin/python benchmarks/pocs/componentize_poc/run_componentize_poc.py
  # scenario 1: p1_print_lifted was "error" although stdout was captured
  ```
  or directly:
  ```
  .venv/bin/python - <<'EOF'
  from ephemora_cell import ComponentSandbox, WASIConfig
  r = ComponentSandbox(WASIConfig(max_fuel=5_000_000)).run(
      "benchmarks/pocs/componentize_poc/p1_print_lifted.wasm")
  print(r.status)  # pre-fix: ExecutionStatus.ERROR  post-fix: SUCCESS
  EOF
  ```
* **Fix applied (one-line semantics, ~9 lines with comment):** in
  `wasi_02.py`, before the generic ERROR return, mirror the preview1 sandbox
  (`wasi_runtime.py` does the same for `proc_exit` traps) and treat
  `exit status 0` as SUCCESS with `exit_code=0`:
  ```python
  if re.search(r"exit status 0", trap_msg):
      return ExecutionResult(status=ExecutionStatus.SUCCESS, exit_code=0, ...)
  ```
  Only the `0` case is special-cased; non-zero exits still report ERROR
  (`wasi:cli/exit` never traps for non-zero in the command adapter — the
  status is returned via the `run` result instead).
* **Why it's safe:** the string `Exited with i32 exit status 0` is emitted
  exclusively by wasmtime's host `exit` implementation on a guest-requested
  clean exit. A genuine trap cannot contain it.
* **Impact on existing tests:** none — `hello02.wasm` returns from `run`
  normally and never hits this path. Full suite at PoC time: 202 passed.

### Finding 2 (fixed) — `ComponentSandbox` never reports `fuel_consumed`

`ExecutionResult.fuel_consumed` was always `None` for the component path
(`wasi_02.py` never read `store.get_fuel()` after run). Preview1 reports it
(`wasi_runtime.py:457-462`). Fixed via `_fuel_consumed(store)` in
`wasi_02.py`: `max_fuel - store.get_fuel()` is computed in all four return
paths (Variant-ok, normal exit, `"all fuel consumed"` trap, `"exit status
0"` trap) and yields `None` only when metering is disabled. Covered by
`tests/test_component.py::TestHelloComponent::test_fuel_consumed_*` (4 new
tests).

### Finding 3 (partially addressed) — `Store.set_limits` bounds linear memory, not the GC heap

GC heap allocations (`struct.new`/`array.new`) are not charged against
`Store.set_limits(memory_size=...)`. A guest that allocates GC objects
without touching linear memory is only bounded by fuel/timeout. The GC PoC
proves it: `gc_workload` (100k allocs) runs cleanly with `max_memory_mb=1`.
This is wasmtime architecture (GC heap is separate from the store's linear
memory limit).

Status: `WASIConfig.max_gc_heap_mb` was added as an observability knob
(validated, recorded in `security_baseline["gc_heap_mb"]`, forwarded through
the worker subprocess). Byte-level *enforcement* remains impossible with
wasmtime-py 47: `wasmtime_store_limiter` binds only memory/table/instances
counts, and upstream's `ResourceLimiter` GC hook is not exposed in the
Python API — fuel remains the effective GC memory bound. Track upstream
wasmtime-py for a GC-heap limiter binding, then the knob becomes the
enforcement point.

### Finding 4 (documented) — `wasm-tools component new` does NOT auto-embed the preview1 adapter

`wasm-tools 1.255.0` requires `--adapt wasi_snapshot_preview1.command.wasm`
(the adapter is not bundled with wasm-tools/wasmtime-py; fetch from the
wasmtime release matching your CLI). Reproduce:
```
wasm-tools component new p1_print.wasm -o out.wasm
# error: failed to resolve import `wasi_snapshot_preview1::fd_write`
wasm-tools component new p1_print.wasm --adapt wasi_snapshot_preview1.command.wasm -o out.wasm
# OK
```

### Finding 5 (documented) — fuel calibration differs between ABIs

Components (lifted or native) burn fuel at different rates than preview1
core modules — same 100k-iteration loop: 3.42M fuel as preview1 core vs
different totals through the adapter (the adapter itself consumes fuel on
every `fd_write`/`proc_exit` hop). No single max_fuel value maps 1:1 across
ABIs; this is already noted in `wasi_02.py`'s module docstring and was
confirmed here. For portable limits, prefer `timeout_seconds` (epoch
interruption) over `max_fuel`.

### Finding 6 (documented) — lifted command modules must export linear memory

The preview1 command adapter imports `env::memory`; a command module with no
exported memory fails lifting (`main module cannot import memory`). Add
`(memory (export "memory") 1)` (all real command modules have one).

### Tooling gotcha (not a sandbox gap)

In wat text, `memory.grow (i32.const 1)` (no outer parens) parses as
`memory.grow` *followed by* `i32.const 1` — the folded operand form requires
`(memory.grow (i32.const 1))` or plain `i32.const 1 memory.grow`. This cost
a debugging round; documented so it isn't rediscovered.
